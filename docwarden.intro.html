DOCWARDEN · 项目文档守护

跑在 GitHub Actions / GitLab CI 上的零依赖工具。它把你的代码库扫成一份能被人读、 也能被 AI 查的模块文档，并且管住新鲜度：源码一变就标失效，没人确认过的不冒充结论。

零依赖 · CI 里不需要 npm install 可作 GitHub Action 直接 uses 引用 Node 18+ · MIT

文档腐烂不是态度问题

几乎每个团队都经历过「文档没法看」的阶段。把它归因为「大家不爱写文档」是错的， 真正让它腐烂的是三个结构性的东西：

① 写文档的收益归别人，成本归自己

你今天花两小时写清楚一个模块，受益的是三个月后接手的人。理性的人会把这时间花在功能上。

② 写了也活不过一个迭代

代码天天改，文档改一次，就没人再改第二次。三个月后它还在，但已经不描述任何真实的东西。

③ 现在 AI 能写了，可没人敢信

模型生成的文档读起来头头是道。问题不是它可能错，而是读的人无从判断该信几分： 没有「谁担保过」的标记，也没人知道它是不是早就过期了。

前两条还能靠「文档过期了我知道」来规避，第三条不行。一份没人确认过、可能已经过时的模型输出， 和一份资深工程师确认过的文档，长得一模一样。

要求开发者记得同步文档，在任何五人以上的团队里都会失败。人一忙，第一个被跳过的就是没人催的那一步。 这不是纪律问题，是必然结果。

这个工具的办法是接在你的 CI 上持续运转，而不是生成一次就完事。

三个关键设计

一、文档必须能承认自己过期了

文档有三种状态，外加「还没生成」这个起点。判定优先级从高到低：

机制上是机器管指纹、人管状态。

  • 源码指纹：对模块覆盖的每个源码文件算内容哈希。它一变，文档立刻标已失效，这一条压过其他所有判断。
  • 正文指纹：算的是文档正文本身。人的确认跟它绑定在一起。
  • 人的确认写在文档自己的头部（front-matter）里，和指纹放在一起。工具只读它，不擅自替你写「已验证」。
状态不单独放一个 status.json。任何模块更新都会改动那个文件，多分支合并必然冲突， 而冲突的内容是一串机器哈希，人没法判断该保留哪一边。把确认和它描述的那份文档放在一起， 冲突就变回「两份文档内容不同」这个人类能处理的问题。
① 用内容哈希，不用时间戳。源码改回去之后，确认会自动重新生效；时间戳做不到，改回去也永远算「旧」。
② 内容变了不删那条确认记录，而是让指纹对不上、自动失效，所以对「人的文件」永远是非破坏性写入。
状态也不能写进正文。正文指纹是判断「人确认的是哪一版内容」的依据，改状态就会改哈希， 那条确认立刻作废，整个机制会自锁。所以状态只走 front-matter。

二、索引由脚本生成，不经模型

产出里会同时生成 INDEX.md，两张表：模块总览（含状态）和一张「文件 → 模块」映射表。

第二张是检索用的关键，知道「我正在改这个文件，该看哪份文档」。它由脚本从扫描结果算出， 一次模型调用都不经过。

索引写错了比文档写错了更麻烦。文档写错了，人读的时候能察觉；索引里写着「退款逻辑在 payment/refund.js」而代码其实已经挪走，AI 会照着去找，在错的地方继续推理， 而且不报错。
模型还有一个问题：每次生成的结果不一样，没法验收。所以索引只能由脚本算。

三、状态跟着内容，一起进 AI 的上下文

文档给人看是一回事，让 AI 在写代码时主动去查是另一回事。这个工具通过 MCP 把知识库暴露给 Cursor / Claude Code 之类支持 MCP 的客户端。

每份交给 AI 的文档，开头都带一行状态。

> 文档状态：**候选**
> **这份文档是「候选」，没有任何人确认过**，内容由模型生成、可能不准确。
> 引用它的结论前请自己核对源码。

不同状态给 AI 的指令是不同的：

状态AI 收到的指令
已验证内容可信，且确认之后源码没动过
候选没人确认过。可以拿它建立印象，但不能当结论引用
已失效生成之后源码改了，以源码为准
状态不跟着内容走，前面那套机制就白做了。AI 会把模型生成的猜测当成团队共识去用， 未经确认的 LLM 输出就获得了它不该有的权威性。

MCP：五个工具

零依赖，自己实现的 JSON-RPC over stdio，不装官方 SDK。它不依赖本地界面在跑， 直接读磁盘上的文档，状态和指纹自己现算。

工具用途典型问法
knowledge_overview列出所有模块与状态「这项目有什么、哪些有文档？」
get_module_doc取某个模块的完整文档「pages 模块是干什么的？」
find_module_for_file文件 → 模块 + 文档「我在改 cart.vue，有什么约定？」
search_docs按关键词搜模块名 / 文件 / 正文「哪里提过退款？」
check_freshness查哪些已失效、哪些没人确认「这些文档现在还能信吗？」

四条边界

不改你的源码

只往 docs/ 和 history/ 写， 而且是开 PR 让你过，不直接推主干。源码逐字节不变。

没有遥测

除了你自己配置的模型接口，不向任何第三方发东西。 不发统计、不回传、不打电话。

不碰你的 key

API Key 走 CI 的 Secret，不落盘：不进任何文件、 不进导出物、不进日志。这条有专门的测试守着。

它守新鲜，不守正确

工具能保证内容新鲜，保证不了内容正确。 后者必须有人做，也只能有人做。它负责把「没人确认过」标出来，不替你把关。

快速开始

# 1. 接进你的仓库
npx docwarden init                     # GitHub，脚本进你的仓库
npx docwarden init --no-vendor         # GitHub，脚本不进你的仓库
npx docwarden init --platform=gitlab   # GitLab

# 2. 装完先体检，再零成本跑一次巡检（不调模型）
npx docwarden doctor
npx docwarden update --mode audit

# 3. 想先看效果再接 CI，可以起本地界面（可选）
npx docwarden serve

# 4. 想让 AI 助手也能查这份知识库
claude mcp add docwarden -- node /path/to/docwarden-mcp.mjs --root /path/to/your-project

接 CI 之前想先看效果，就拿自带的 sample/ 目录、在本地界面里选「演示模式」跑一遍。 不需要配任何模型，秒出结果，用来确认流程和排版。之后再换成真实项目和你自己的模型接口。

装完之后只有一件事需要你下判断，就是复核模块划分。工具只看目录树推断模块边界， 看不懂你的业务边界。

云端接口会把源码发出去。填 https:// 开头的公网地址，你的源码就会被完整发送到 那家厂商的服务器上。拿样例试没问题，公司项目的代码不要这么干，除非你确认过安全规定允许。 内网部署的模型（127.0.0.1 之类）没这个问题，慢一点，但代码不出你的网络。

再说一类它处理得不错的情况。仓库里常有名字和内容对不上的文件，比如 src/utils/tmp.js 看着像用完就该删的临时脚本，实际是一整套还在被引用的业务规则。生成的文档不会把它糊过去：

文件名与内容不符：tmp.js 命名像临时脚本，实际包含完整的业务规则， 且被导出使用；不要当作可删除的临时文件 [待确认：该文件是否仍被引用，还是仅为历史快照]

点出问题、警告别误删，再用 [待确认] 收口，不替人下结论。这是它对历史包袱的态度： 如实记录，不美化成一个设计模式。
