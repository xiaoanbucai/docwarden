# 装进仓库之后 · 使用说明

这是 `docwarden` 落到**你的仓库里**的那一部分怎么运作。零依赖，Node 18+，CI 里不需要 `npm install`。

装进去一条命令：

```bash
npx docwarden init                     # GitHub + vendor 模式（脚本进你的仓库）
npx docwarden init --no-vendor         # GitHub + 引用模式（脚本不进你的仓库）
npx docwarden init --platform=gitlab   # GitLab（只有 vendor 模式）
npx docwarden init --dry-run           # 先看会写哪些文件
```

> **两种接入方式**：引用模式（`--no-vendor`）下你的仓库里**没有 `scripts/`**，
> CI 里用 `uses: <org>/docwarden@v1` 直接调工具，靠 `--root` 指到你的工作区。
> 本文其余部分对两种模式都成立 —— 差别只在「脚本放在哪」，不影响它怎么运转。
>
> **本文档描述的是 vendor 模式的目录形态。** 引用模式没有 `scripts/`，
> 第四节「手动模式说明」里的命令要换成 `npx docwarden update --mode …`。
> 两种方式的取舍见根目录 [README](../README.md) 第一节。

装完随时可以体检：

```bash
npx docwarden doctor
```

> 手工对照文件清单拷贝也可以（见第二节），但没必要 —— `init` 会顺带探测你的目录结构，
> 生成一份 `.knowledge.mjs` 初稿，并处理好 `.gitignore` 与 CI 的目标路径。

---

## 一、30 秒理解它做什么

```
你提 PR        → CI 生成「文档影响预览」，贴在 PR 里（不写入任何文件）
你合并主干     → CI 重生成受影响模块的文档，开一个 PR
你打 Release   → CI 生成版本演进章节，写入 history/
每天凌晨       → CI 巡检，找出文档与代码脱节的模块并修复
```

**它不做的事**（很重要，避免期待错位）：
- 不记录每个 commit 的流水账（git 已经做得更好）
- 不追踪未合并分支的进度（那属于项目管理工具的职责）
- 不改你手写的 `docs/decisions/` 和 MANUAL 块
- 不判断代码风格（那是 ESLint 的活）

## 二、文件清单和放置位置

下面是 **vendor 模式**下 `init` 会产出的全部东西，也是手工拷贝时的对照表
（引用模式没有 `scripts/` 那一段）：

```
你的仓库/
├── .knowledge.mjs                    ← 配置（init 依据你的目录结构生成初稿）
├── .gitignore                        ← 加一行 .docs-preview.md
├── docs/
│   ├── README.md                     ← init 生成，给同事看的说明
│   ├── current/
│   │   ├── INDEX.md                  ← 自动生成：模块清单 + 功能索引 + 新鲜度
│   │   └── modules/                  ← AI 生成，可覆盖
│   ├── history/releases/             ← 只在打 tag 时写入
│   └── decisions/                    ← 你手写，AI 永不触碰
├── scripts/
│   ├── docs-update.mjs               ← 主脚本
│   ├── lib/
│   │   └── freshness.mjs             ← **必须一起拷**，见下方说明
│   └── prompts/
│       ├── module.md                 ← 模块文档提示词
│       └── chapter.md                ← 版本章节提示词
├── .github/workflows/docs.yml        ← GitHub 的四个触发契机
│   或 .gitlab-ci.yml                 ← GitLab 的四个触发契机
└── .github/pull_request_template.md  ← 强制填写决策三问
    或 .gitlab/merge_request_templates/Default.md
```

> **`scripts/lib/freshness.mjs` 不能漏。** 指纹算法与状态判定只有这一份实现，
> 主脚本用相对路径 `./lib/freshness.mjs` 引用它，少了它一启动就报找不到模块。
> 它同时也是本地工作台和 MCP 服务的引用对象 —— 两边共用同一份，才不会出现
> 「一边生成的文档另一边认不出、于是反复判成失效、反复重新生成」这种白烧额度的情形。

另外两个文件：

| 文件 | 用途 |
|---|---|
| `SETUP.md` | **配置指南**：模型怎么选、密钥放哪、权限怎么开、本地怎么验 |
| `templates/pull_request_template.md` | PR 模板：强制填写决策三问，这是文档拿不到的那部分信息 |

## 三、落地五步

### 第 1 步 · 建人写内容的地基

目录 `init` 已经建好了。你要做的是**在 `docs/decisions/` 下随便写一篇** `0001-项目背景.md`。
这个目录的作用是告诉团队：**这里是人写的地方，AI 不碰。**

### 第 2 步 · 复核配置（唯一需要你下判断的地方）

打开 `init` 生成的 `.knowledge.mjs`，复核 `modules` 和 `sourceRoots`。

**推断只看目录，看不懂业务边界**，所以它给的只是初稿：它可能把两个本该合并的目录拆成
两个模块，也可能把不相关的东西归到一块。这一步花十分钟，能省掉后面反复调整的麻烦。

**划分原则：** 太细会让文档碎片化，太粗会让每次小改动都重生成一大堆。**建议一个模块 5~30 个文件**，参照你们现有的目录划分。

> ⚠️ 配置会随时间腐烂。一旦目录重构、`.knowledge.mjs` 里的路径就失效了，模块静默失配、文档从此不再更新，**而且不会有任何报错**。所以巡检（第四步）专门做了配置体检；平时也可以直接跑 `npx docwarden doctor`。

### 第 3 步 · 配模型（必须你自己填）

配置里的 `llm` 段是**故意留空的**：这个脚本会把源码读出来发给模型，填哪个地址就等于把
源码交给谁。所以工具不预填任何厂商、也不会用默认地址偷偷跑起来 —— 没配就报错，
报错里给出下面两种配法。

```bash
# ① 环境变量（CI 里就是这么配的）
export LLM_BASE_URL="https://你的服务/v1"
export LLM_MODEL="模型名"
export LLM_API_KEY="sk-xxx"

# ② 或者直接改 .knowledge.mjs 的 llm 段（适合固定用某个模型）
#    apiKey 仍然只能走环境变量
```

CI 里配成 Secret / 加密变量，不要写进代码。

> **红线**：`LLM_BASE_URL` 填 `https://` 公网地址，就意味着源码会完整送到那家厂商。
> 公司项目请先确认安全规定；要用就用内网部署的模型 —— 那是内网地址，不出网，
> 脚本本身不用改。

**模型怎么选、密钥在哪配、权限怎么开——见 [SETUP.md](SETUP.md) 与
[USAGE.md](../USAGE.md)。** 其中「GitHub 要开 Workflow 写权限」这条特别容易漏：
漏了不会有任何报错，只是永远开不出 PR。

### 第 4 步 · 接上 CI，并用手动触发验收第一次产出

配置 `init` 已经放好了（GitHub → `.github/workflows/docs.yml`，GitLab → `.gitlab-ci.yml`），
四个契机的关键点都写在注释里。剩下的是**开权限**：

- GitHub：`Settings → Actions → General → Workflow permissions` 选 **Read and write**
  （不开的话机器人跑得再对也开不出 PR，而且不会有明显报错）
- GitLab：加一个带 `write_repository` + `api` 权限的 `DOCS_BOT_TOKEN`

接的时候有四个坑，都是踩过才知道的：

| 坑 | 现象 | 处理 |
|---|---|---|
| 机器人提交不触发下游流程 | 用默认 Token 创建 PR，不会触发其他 workflow，CI 门禁形同虚设 | 改用具备触发权限的 Token，或调整门禁的挂载方式 |
| 自我触发循环 | 文档提交又触发文档任务，无限递归 | 必须配 `paths-ignore: docs/**`（GitLab 侧是在 `changes:` 里不写 `docs/**`） |
| 首次推送基准为空 | 新分支第一推时基准提交是全零，diff 直接算不出来 | 脚本已处理：检测到全零回退 `HEAD~1` |
| 定时任务里 `changes:` 恒真 | GitLab 的 `changes:` 规则在定时流水线中永远成立，等于每次全量跑 | 定时任务中不要使用 `changes:` 规则 |

**然后别一上来就交给事件自动触发。** 先手动跑一次
（GitHub 的 `workflow_dispatch` / GitLab 的 Run pipeline），让它在你的仓库里真跑一遍，
确认整条链路是通的、并且产出合格。

这一跑同时就是**质量验收**，比后面所有步骤都重要。看它开出来的那个 PR：

- 读起来像不像人话？
- 有没有编造代码里不存在的功能？（重点）
- 描述的是「职责和流程」还是「复述代码」？

**质量不行，先别开自动触发。** 改提示词再手动触发一次 —— 把 `prompts/` 拷到你仓库的
`scripts/prompts/` 下就行（只放提示词、不放脚本），脚本会让**你的那份优先**，
引用模式下也照样生效。

链路通了、产出也合格，再把它交给 push / PR / tag / 定时这四种事件。

### 第 5 步 ·（可选）本地先看一眼，不占 CI 配额

不想等 CI 排队、或者想先摸清产出长什么样，可以在本地用同一套逻辑跑：

```bash
npx docwarden update --mode incremental --base=HEAD~5   # 生成
npx docwarden update --mode preview --base=HEAD~5       # 预览
npx docwarden update --mode audit                       # 体检（不调模型，零成本）
```

> 两种接入方式都适用：引用模式下它会自动用工具自带的脚本，并把目标指到你当前目录；
> vendor 模式下等价于 `node scripts/docs-update.mjs …`。

**本地与 CI 是同一份实现**，所以本地满意了，CI 上的结果也一致。
想要图形界面就 `npx docwarden serve`（扫描 → 划分 → 逐篇生成 → 逐篇人工确认）。
这一步纯属可选的加速手段，不做也完全能跑通。

## 四、手动模式说明

| 模式 | 什么时候用 | 写什么 |
|---|---|---|
| `incremental` | 主干合并后 | `docs/current/modules/*.md` |
| `preview` | PR 阶段 | `.docs-preview.md`（临时，不提交） |
| `chapter` | 打 Release tag 后 | `docs/history/releases/<版本>/chapter.md` |
| `audit` | 每日定时 | 只报告；加 `--fix` 才修复 |

常用参数：

```bash
--base=HEAD~5     指定比对起点（CI 里会自动推断）
--force           忽略代码指纹，强制重新生成
--dry-run         只打印不写文件
--fix             audit 模式下直接修复漂移
```

## 五、人写内容怎么保护

AI 只会整篇重写 `docs/current/` 下的文件。你想在模块文档里加一段自己的说明，用标记块包起来：

```markdown
<!-- MANUAL:BEGIN -->
## 业务背景与取舍

当初改用集中式状态机，是因为早期分散写入导致过两次线上事故。
<!-- MANUAL:END -->
```

**重新生成时脚本会先把这段摘出来，生成完再原样放回去。** 一个字都不会动。

这条机制的意义：即使 AI 生成出了问题，**影响面也被锁在 AI 区域内**，你手写的核心内容不受牵连。

## 六、文档状态：候选与已验证

每份文档头部都记着自己的状态。这不是装饰 —— **它决定 AI 能不能把这份文档当结论用**。

| 状态 | 含义 | 由谁造成 |
|---|---|---|
| **候选** | 模型刚生成，**没有任何人确认过** | 生成时自动写入 |
| **已验证** | 有人确认过，且确认之后源码与正文都没再变 | **只有人**能把候选改成这个 |
| **已失效** | 文档生成之后源码变了 | 判定时自动得出 |

规则只有两条：

1. **源码变了 → 一律「已失效」**，压过一切。文档在描述旧代码，比没有文档更危险。
2. **正文被重新生成过 → 确认作废**，退回候选。确认绑定的是**那一版内容**，不是模块名。

指纹和「谁确认过」都写在文档自己的头部（front-matter），**不设独立的 status.json**：
任何模块更新都要改动同一个文件，多分支合并必然冲突，而冲突内容是一串机器哈希，
人没法判断该保留哪一边。

> **「已验证」这件事，机器替不了。** 没人去点确认，文档就永远是「候选」。
> 工具能保证内容**新鲜**，保证不了内容**正确** —— 后者必须有人做，也只能有人做。

### 索引里那两列别混

`INDEX.md` 的模块清单里有两列看着像、作用完全不同：

- **状态** —— 看时间。超过 30 天未更新会标「可能过期」。
- **人工确认** —— 看有没有人担保过内容。

一份昨天刚生成的文档可能仍是候选；一份三个月前的文档可能早就被确认过。两列互不替代。

## 七、功能索引与新鲜度

模块文档生成后，脚本会顺手汇总出一份 `docs/current/INDEX.md`，里面有两张表。

**模块清单**：每个模块的文档链接、最近更新时间、距今天数、状态、人工确认。超过 30 天未更新的会被标成「可能过期」—— 给文档建立时间感，避免有人照着一份三个月前的说明去改代码。「人工确认」列直接读自文档头部，显示有没有人担保过这份内容（两列的差别见第六节）。

**功能索引**：功能点 → 涉及哪些模块。

| 功能点 | 说明 | 涉及模块 |
|---|---|---|
| 退款 | 用户发起退款申请，审核通过后原路退回 | order / payment |
| 订单取消 | 未支付订单可由用户主动取消 | order |

这张表解决一个具体的错位：**人提问的最小单位是「功能」，文档的最小单位是「模块」。** 有人问「退款怎么走的」，而退款逻辑横跨订单、支付、财务三个模块——任何单篇模块文档都答不完整。有了这张表，检索才能先定位到相关模块。

功能点由模型在生成模块文档时顺手产出（写在提示词要求的 `FEATURES` 块里），脚本提取后写进文档头部元数据，再从正文中移除。**不需要人工维护**，成本接近零——但等模块多了再补，就要全量重跑一遍。

> 命名一致性很关键：同一件事在不同模块里必须叫同一个名字，否则索引会分裂成多条。这一点已经写进提示词，但抽查时仍需留意。

## 八、日常会遇到的问题

按危害排序。**前四条不会报错，所以最危险**——它们会安静地让你的文档停止更新。

| 问题 | 症状 | 怎么防 |
|---|---|---|
| **配置腐烂** | 目录重构后路径失效，文档静默停更，流水线全绿 | 巡检的配置体检会报出「路径失效」 |
| **新目录漏配** | 新建的功能目录不在配置里，永远没有文档 | 巡检统计「未覆盖的源码文件」 |
| **幽灵文档** | 模块删了，文档还在描述它 | 巡检列出「已不在配置中的文档」 |
| **无人使用** | 生成了但没人看，慢慢腐烂 | 前两个月观察，没人用就说明产出形式不对 |
| 文档 PR 堆积 | 没人合并，攒了几十个 | 文档 PR 极简，看两眼就能过；或设自动合并 |
| 模型服务超时 | CI 任务整体失败 | PR 预览用了 `continue-on-error`；正式更新可加重试 |
| 巨型变更 | 重构或冷启动时一次生成全部模块 | 分批引入，一次一个模块；`maxChangedFiles` 兜底 |
| 大模块生成不完整 | 代码超过两三千行，输出被截断，模型开始自行摘要 | 把模块拆到 1500 行以内——**「模块」按行数定义，不按目录** |
| 永远没人补充「为什么」 | 文档只答「是什么」，新人依然卡在设计取舍上 | PR 模板强制三问；文档回链 PR。这部分 AI 写不出来，别指望它 |
| 换模型后质量断层 | 新旧模型写的文档混在一起，无法区分 | 元数据记录 `model` / `prompt_version`；全量重刷走独立 PR，只抽样 review |

**判断标准很简单：** 如果一个故障"不报错"，它就必须靠**主动巡检**发现，不能指望它自己暴露。

## 九、分支问题怎么处理

文档放在仓库里，就会继承分支语义：

| 情况 | 是否正常 | 怎么办 |
|---|---|---|
| 老分支看不到 `docs/` | 一次性问题 | 合并主干即可，之后新切的分支都会有 |
| 老分支看到的是旧文档 | **正常，且正确** | 不用管。老分支代码是旧的，文档就该是旧的 |
| 合并时代码和文档冲突 | 真问题 | 见下 |

**⚠️ 千万别做：** 不要用 `git checkout main -- docs/` 把主干文档单独塞进老分支。文档描述的是主干代码，你分支上的代码是旧的，两边会对不上——**带错的文档比没有文档更危险。**

**冲突的缓解措施：**

1. **指纹写进文档头部，不用独立状态文件。** 集中存放意味着任何模块的更新都会改动同一个文件，多分支合并时必然冲突；而且冲突内容是一串机器哈希，人工无法判断该保留哪一边。指纹直接写进每份文档的 front-matter 后，冲突面降到「单个模块文件」，并随文档一起版本化。
2. **AI 只往主干写，且走独立 PR。** 不在 feature 分支上生成正式文档。
3. **人写内容用 MANUAL 块隔离**，几乎不会被多个分支同时改。
4. **长命分支早合主干。** 这是 git 常识，不是本方案带来的新问题。

建议在 `docs/README.md` 里写一句给同事看：

> 本目录内容由 CI 自动生成，描述的是**主干当前状态**。如果你在 feature 分支上，看到的文档可能对应旧的代码——以代码为准。

## 十、什么时候该升级到独立仓库

出现这些信号时，把 `docs/` 搬到一个独立的 `team-knowledge` 仓库：

- 要在**多个项目之间**统一检索、问答
- 想让产品、测试同学也能看文档，但不想给他们业务仓库权限
- 长命分支太多，文档冲突开始影响正常开发

迁移成本不高：移动文件 + 改 CI 的目标仓库。先跑起来验证价值，不用现在纠结。

## 十一、下一步

跑完第四步之后，把生成的文档发出来看一眼，判断：
- 生成质量够不够交付给团队
- 提示词该怎么调
- 模块划分合不合理

如果决定往团队推，**先在一个仓库试点，验证两周再铺开**——一次推五个仓库会很狼狈。

## 附：脚本内部的两条铁律

**一、依据 vs 参照**

生成模块文档时，**旧文档只作为格式参照，不作为内容依据。** 内容必须从代码重新得出。

为什么不直接给旧文档"打补丁"？因为旧文档里每一句话都可能已经失真，而你无法判断哪一句还成立——这是幻觉滚雪球的真正来源。而且从成本看，打补丁要把旧文档也喂给模型，**输入反而比重生成更大**。

**二、代码指纹缓存**

每个模块的代码内容算一个 SHA256 指纹，写进文档头部。指纹没变就**完全跳过**，一次模型调用都不发。

这是省 token 最有效的一条：日常提交往往只动一两个模块，其余模块连读都不读。

指纹的算法与「加框方式」也定义在同一个文件里（`scripts/lib/freshness.mjs`）。
所谓加框，是每个文件写成 `路径 NUL 字节数 NUL 内容 NUL` 而不是裸拼接 ——
这样文件边界永不含糊，不会出现「A 的结尾 + B 的开头」拼出与另一组文件相同字节流的情况。

**换算法时不会误伤**：判定同时认得历史算法算出的旧值。源码没变、只是指纹换了算法时，
脚本只把文档头部就地升级一下，**不重新生成**。为算法换代重跑一遍模型，是纯粹的浪费。
