## 内容结构

用 Markdown 输出，按以下结构组织（没有内容的章节直接省略，不要写"暂无"）：

### 模块职责
一到三句话说明这个模块解决什么问题、在系统中的位置。

### 核心流程
描述主要业务流程或数据流。用有序列表。只描述代码中确实存在的流程。

### 关键设计
列出这个模块里值得注意的设计选择、约定、约束。例如状态如何流转、边界条件如何处理、有哪些隐含前提。

### 对外接口
如果模块对外暴露了函数、组件、事件、API，列出名称、作用、关键参数。用表格。

### 注意事项
容易踩坑的地方：不易察觉的副作用、依赖的执行顺序、特殊场景的处理。

## 功能清单

正文写完后，另起一段，列出这个模块实现的、用户或系统可以感知的能力。脚本会把这些条目汇总成一张跨模块的功能索引——这是「按功能提问」能被检索到的唯一依据。

格式固定，**不要改动 `FEATURES` 标记**：

```
<!-- FEATURES
退款：用户发起退款申请，审核通过后原路退回
订单取消：未支付订单可由用户主动取消
-->
```

要求：

- 每行一条，格式为 `功能名：一句话说明`。
- 功能名用简短的名词短语（2–6 个字）。**跨模块描述同一件事时命名必须一致**——不要一个模块写「退款」、另一个写「退货申请」，否则索引会分裂成两条。
- 只列这个模块**自己实现**的功能，不要列它调用的、由别人实现的功能。
- 没有可列的功能，就输出空的标记块。
- 这段内容不会出现在最终文档里，脚本提取后会自动从正文中移除。

## 硬性约束（必须遵守）

1. **只描述代码中实际存在的行为。** 不要推测、不要脑补、不要"一般来说"。如果代码里没写，就不要说。
2. **不要复述源码。** 不要粘贴大段代码实现，不要逐行解释变量。你要描述的是**职责与流程**，不是代码本身。整篇文档的代码块不应超过 3 个。
3. **不确定的地方必须标注。** 用 `[待确认]` 标记出来，不要用模糊语言掩盖。例如：「该方法在超时后的重试次数为 `[待确认]`」。
4. **保留专有名词原样。** 接口名、字段名、函数名、枚举值一律使用代码中的原始写法，用反引号包裹。不要翻译、不要改写。
5. **不要写主观评价。** 不要出现"设计得很好""性能优秀""代码优雅"这类判断。
6. **不要在结尾加总结段。** 写完最后一个有内容的章节就结束。
7. **不要加一级标题。** 从 `##` 开始，因为文件名已经表达了模块名。
8. **不要写「业务背景」「设计取舍」「为什么这么决定」这类内容。** 这部分由人工维护，脚本会自动保留它们，你写了反而重复。
9. **不要输出 `MANUAL` 相关的 HTML 注释标记。** 那是给脚本用的，不是给你用的。
10. **不要把「代码里存在」写成「团队认可」。** 存量代码里的临时降级开关、为某次故障加的兼容分支、废弃但未删除的逻辑、被注释掉的实现，要如实描述其存在与作用，但**不得表述为推荐做法、设计模式或最佳实践**。无法判断它是长期设计还是历史遗留时，标注 `[待确认]`，并只写你观察到的事实——例如「该分支在某条件下启用 `[待确认]` 是否仍在使用」。这类"把仓库现状读成组织规范"的描述会被后续生成反复引用，从而把一个历史包袱固化成团队标准。
