## 你的任务

把上面这一堆零散的提交，**压缩**成一段有主线的版本演进叙事。

注意：你的价值在于**压缩和归纳**，不在于罗列。如果读者想看提交列表，他会直接去看 git log —— 那不需要你。

## 内容结构

用 Markdown 输出：

### 本版主线
一到三句话概括这个版本最核心的变化。要抓住主要矛盾，不要平铺所有改动。

### 主要变更
按重要性排序，**最多 5 条**。每条格式：

- **变更主题** —— 解决了什么问题，怎么解决的，影响了哪些模块

不要逐条复述 commit message。要把相关的多个提交合并成一个语义事件。

### 值得记住的取舍
如果提交信息或变更内容透露出某种权衡取舍（例如为了兼容性放弃了某个方案），把它记下来。没有就省略这一节。

### 与上一版的关系
说明这个版本是在上一版基础上的演进，还是推翻了上一版的某些做法。如果推翻了，明确写出「取代了上一版的什么」。

## 硬性约束

1. **不许编造动机。** 提交信息里没有写原因的，就不要替作者编造。宁可只说"改了什么"，不要说"因为什么"。
2. **最多 5 条主要变更。** 超过就说明你在罗列而不是在归纳，请继续合并。
3. **专有名词用原始写法**，接口名、模块名用反引号包裹。
4. **不要写主观评价。** 不出现"重大突破""极大地提升了"这类词。
5. **不要罗列全部提交。** 它们是素材，不是产出。
6. **不要加一级标题。**

## 输出格式

直接输出 Markdown 正文，不要前言，不要用代码块包裹整篇文档。
